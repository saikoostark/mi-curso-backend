# Agent Guidelines (AGENTS.md)

Backend for a courses/e-learning application, built incrementally feature by feature. NestJS 12, ESM, Vitest, oxlint, Postgres 18 + TypeORM, Redis 8 — details below.

## ESM project — relative imports need `.js` extensions
- `package.json` sets `"type": "module"`; tsconfig uses `module`/`moduleResolution: "nodenext"`.
- Every relative import must end in `.js` even though sources are `.ts`: `import { AppService } from './app.service.js'`.
- `nest g` schematics already emit `.js`; hand-written imports must match or Node throws `ERR_MODULE_NOT_FOUND`.

## Toolchain differs from NestJS defaults
- Tests use **Vitest**, not Jest: unit `**/*.spec.ts`, e2e `**/*.e2e-spec.ts`.
- Lint uses **oxlint** (`oxlint --type-aware src/ test/`), not ESLint. `typescript/no-floating-promises` is an error; `typescript/no-explicit-any` is off.
- Prettier (single quotes, trailing commas) runs via `npm run format` and covers only `src/**` and `test/**`.
- Vitest prints a `vite-tsconfig-paths` migration nudge — harmless, ignore it.

## Commands
- Dev server: `npm run start:dev` (watch; port from `PORT` env or 3000). Check if an instance is already running before starting another.
- Swagger UI: `/docs` (`/docs-json` for the OpenAPI document) once the app is running.
- Build/production: `npm run build`, then `npm run start:prod` (`node dist/main`).
- Single unit test: `npx vitest run src/app.controller.spec.ts`.
- Single e2e test: `npx vitest run --config ./vitest.config.e2e.ts test/app.e2e-spec.ts`.
- No dedicated typecheck script; `npm run build` (tsc via `tsconfig.build.json`) and type-aware lint are the checks.
- Migrations (TypeORM CLI via `tsx`; the scripts load `.env` with `node --env-file=.env` and fail loudly when it is missing):
  - `npm run db:migration:create -- src/database/migrations/Name` — empty migration.
  - `npm run db:migration:generate -- src/database/migrations/Name` — diff entities against the DB.
  - `npm run db:migration:attributes -- src/database/migrations/Name` — attribute-catalog seeder (see Authorization).
  - `npm run db:migration:run` / `npm run db:migration:revert`.
- `npm run create-superuser` — bootstraps a verified superuser; interactive, or one answer per line piped to stdin (username, email, password, confirmation). Validates like registration and aborts when username/email are taken.
- `npm run test:e2e` requires `.env`, a reachable Postgres and Redis; specs run against the dedicated `DATABASE_URL_TEST` database and `REDIS_URL_TEST` logical DB (created manually — see Infrastructure) with pending migrations applied first.

## Testing conventions
- Both configs set `globals: true`: use `describe/it/expect` without imports.
- Unit specs live next to their source in `src/`; most instantiate the class under test directly and inject `vi.fn()` mocks (`Test.createTestingModule` where DI wiring itself matters). Mock external dependencies.
- E2E specs live in `test/` and use supertest (`import request from 'supertest'`; `App` type from `supertest/types.js`).
- Integration tests should wire real modules together rather than mocking the app under test.
- E2E apps must be built with `createE2eApp()` (`test/setup/app.ts`) — it applies `configureApp()` (cookie-parser, `TRUST_PROXY`, global ValidationPipe) exactly like `main.ts`. The global response interceptor and exception filter are registered on `AppModule`, so e2e responses use the same envelope as production.
- Success assertions read `.body.data`; paged lists read `.body.data.page` and `.body.data.pagination`; errors read `.body.error.code` / `.body.error.meta`. Raw infrastructure routes (`/health`, `/ready`, `/metrics`, `/`) opt out of the envelope.
- E2E runs boot the app against the dedicated test database and the dedicated Redis logical DB: `test/setup/global-setup.ts` refuses to run when `DATABASE_URL_TEST`/`REDIS_URL_TEST` are not distinct from the dev values (tests truncate data and clear keys), pings Redis and applies pending migrations first; `test/setup/load-env.ts` then redirects the app in every worker (database, Redis, email outbox). Nothing creates databases — `DATABASE_URL_TEST` must already exist.
- **E2E files run sequentially** (`fileParallelism: false` in `vitest.config.e2e.ts`): every spec truncates shared tables, so parallel files would wipe each other's data. The e2e config also raises the test/hook timeout to 30s: password flows run scrypt hashes, and Vitest's 5s default can time out a slow test while it keeps running — the next test's truncation then cascades into 401/400 and FK failures.
- E2E specs truncate the data they touch (`refresh_tokens, auth_tokens, users CASCADE` for auth; authorization specs also truncate `groups` and `audit_logs` — but never `attributes`, the catalog is owned by migrations), clear their own `auth:*`/`audit:rl:*` Redis keys (`test/setup/redis.ts`, `KEYS`-based on purpose) and read emails from the test outbox (`test/setup/outbox.ts`, `findLatestEmail` + `extractToken`) in `beforeEach`; the test database is disposable and developer data lives in `DATABASE_URL`. A health spec asserts the app really is connected to the test DB and that `/ready`/`/metrics` report it.
- `test/setup/authorization.ts` seeds verified accounts straight through the `DataSource` (bypassing the email flow; `hashPassword` from `src/`) and logs them in (`loginForToken`, `bearer`); specs exercise the API paths for everything they assert on.
- Auth e2e note: clearing Redis per test also resets rate-limit counters, so tests stay under the login IP limit; don't exceed ~6 login attempts per test.

## Infrastructure — Postgres + TypeORM
- Postgres 18 runs in the user's Docker container (localhost:5432). Databases are picked via env: `DATABASE_URL` for the app, `DATABASE_URL_TEST` for e2e (dedicated + disposable); nothing auto-creates databases — create them manually.
- Wiring lives in `src/database/`: `data-source-options.ts` holds side-effect-free option builders (safe for the app to import), `data-source.ts` is the CLI-only entry point (`-d src/database/data-source.ts`), and `database.module.ts` registers `TypeOrmModule.forRootAsync` from `DATABASE_URL`. Feature modules own entities via `TypeOrmModule.forFeature` and inject repositories.
- `synchronize` is always `false`; the schema changes only through migrations in `src/database/migrations/` (tracking table: `typeorm_migrations`). CLI entity/migration globs target `src/**` TypeScript sources because the CLI runs through `tsx`.
- Generated migrations must import TypeORM **types** with `import type` (`import type { MigrationInterface, QueryRunner } from 'typeorm'`): the e2e global setup loads migration files through plain Node, whose built-in TypeScript support does not elide value-imports that are only used as types. It uses `buildMigrationRunnerOptions()` (migration glob only, no entities) for the same reason — entity files carry decorators, which plain Node cannot strip, so they may only be loaded via `tsx` (CLI) or Vitest (the app).
- ESM entity gotchas (TypeORM 1.x): relation properties need the `Relation<T>` wrapper; legacy APIs (`Connection`, `findByIds`, `findOneById`) are gone.
- `GET /health` is a pure liveness probe (`HealthModule`): `200` with `{ status: 'ok' }` whenever the process serves requests — it pings no dependencies on purpose. `GET /ready` checks Postgres (`SELECT 1`) and Redis (`PING`) with a 2s timeout each and answers `503` when either is down; `GET /metrics` returns native JSON process telemetry plus the same dependency checks (no Prometheus dependency) and is protected by `METRICS_TOKEN` only when that variable is set.
- Redis 8 (Docker, localhost:6379, **password-protected**): selected via `REDIS_URL` (app, logical DB `/0`) and `REDIS_URL_TEST` (e2e, `/1`). `src/cache/` wraps node-redis v6: the abstract `CacheService` port (JSON values, TTLs in **milliseconds**, `ping/get/set/delete/increment/ttlMs`, sorted-set `zadd/zscore/zremRangeByScore/zcard`) is bound in the global `CacheModule` to `RedisCacheService` — connects on module init, quits on shutdown, error listener attached. Only that adapter may import node-redis; consumers inject `CacheService`.
- Audit: `src/audit/` owns the append-only `audit_logs` table and a global `AuditInterceptor` that records every successful/failed `POST`/`PUT`/`PATCH`/`DELETE` with route pattern, actor (when authenticated), target, IP, user-agent, status and outcome — never bodies, query strings or cookies. `GET /audit-logs` is admin-only via `audit:read`; rows expire after `AUDIT_LOG_RETENTION_DAYS` (default 365) in `TokenCleanupService`.
- Performance: `pg_trgm` GIN indexes back the `%term%` searches on user email/username/profile names and audit actions; the composite `(createdAt, id)` index serves the default user-list reverse scan.
- Email: the abstract `EmailService` (`src/email/email.service.ts`, holds the `OutboundEmail` type) decouples flows from delivery; `FileEmailService` appends JSON lines to `outbox.jsonl` and writes readable `.txt` files under `EMAIL_OUTBOX_DIR` (default `var/email-outbox`, gitignored). The module binds port → adapter; swap the adapter when a real sender lands.
- HTTP logging is `nestjs-pino` (`LoggerModule.forRoot` as the first `AppModule` import): `silent` in tests, `info` otherwise; `req.headers.authorization` and `req.headers.cookie` are redacted; development renders with `pino-pretty` (devDependency — production must boot with `NODE_ENV=production` so the JSON logger is used). `main.ts` creates the app with `bufferLogs: true` and calls `app.useLogger(app.get(Logger))`.
- Deferred on purpose: OpenTelemetry + Grafana stack at deploy (ESM needs `--experimental-loader=@opentelemetry/instrumentation/hook.mjs` plus `--import`); a real email provider.

## HTTP responses — envelope, pagination, errors, Swagger
- Every controller result is wrapped by `ApiResponseInterceptor` (`APP_INTERCEPTOR` in `AppModule`) into `{ success: true, data }`. Paged endpoints return `{ success: true, data: { page: T[], pagination: { page, limit, total, totalPages, hasNext, hasPrevious } } }` — the list is `data.page` by contract.
- Paged query DTOs extend `PaginationQueryDto` (`src/common/http/pagination.ts`): default `page=1`, `limit=25`, max 100, converted from query strings before validation. Metadata is built with `buildPaginationMeta`.
- `ApiExceptionFilter` (`APP_FILTER`) normalizes every failure to `{ success: false, error: { code, message, details?, meta? } }`. Domain exceptions keep their `{ code, message }`; validation errors use code `validation_failed` with `details: [{ field, message }]`; extra domain context (for example `required` attribute keys) moves to `meta`. Unexpected errors are logged and hidden behind a generic 500.
- Error codes are typed `as const` maps owned by the module that raises them (`USER_ERRORS`, `PASSWORD_ERRORS`, `AUTH_ERRORS`, `TOKEN_ERRORS`, `ATTRIBUTE_ERRORS`, `ADMIN_USER_ERRORS`, `GROUP_ERRORS`), with generic HTTP/validation fallbacks in `COMMON_ERROR_CODES` (`src/common/http/error-codes.ts`). Throw sites and specs assert via the constants, never string literals; a unit spec enforces unique lowercase snake_case values. Existing values are stable public contract.
- `ValidationPipe` is configured in `configureApp` with the shared exception factory (`flattenValidationErrors`), so `main.ts` and e2e validate identically.
- Infrastructure routes that are not application resources opt out with `@SkipApiEnvelope()`: `/health`, `/ready` and `/metrics` stay raw, and readiness/metrics/root stay hidden from Swagger.
- Swagger is `@nestjs/swagger`: decorators live on controllers/DTOs, the CLI plugin (`nest-cli.json`) fills request DTO metadata, and `setupSwagger` serves UI at `/docs`. Security schemes are `access-token` (bearer) and `refresh-cookie` (the httpOnly refresh cookie).
- `src/common/http/` owns the envelope, pagination primitives, interceptor, exception filter, shared error/message DTOs, generic error-code map and the standard-error decorator; `src/common/swagger/` owns the document setup. Domain code stays in its owning module.

## Auth — identity & sessions
- Identity & authentication live in `src/identity/`: `auth/` with four journey slices (`registration/`, `session/`, `account/` — which owns the shared password-update tail, profile edit, self-deletion and two-sided email change — and `recovery/`, each controller + service + dto + spec), shared auth types/mailer, plus `token/`, `password/`, `users/` (account + profile primitives), the shared authorization domain (`groups/` entities + manifests, `attributes/` engine, `guards/`, `decorators/`), composed by `IdentityModule`. Administration lives in `src/admin/` (per-resource `users/`, `groups/`, `attributes/`, `audit/` sub-modules composed by `AdminModule`). The global `src/audit/` module owns audit persistence/interception. No separate Users/Authorization modules and no `forwardRef` anywhere.
- Account and profile are separate 1:1 tables: `users` holds identity/credentials/state, `user_profiles` holds only `firstName`/`lastName`/`phone` (shared `userId` PK/FK, cascades). `UserProvisioningService` is the only creation path and inserts both rows in one transaction; nothing creates a lone account. Self-service reads (`/auth/me`, login, refresh) flatten both rows into `UserView`, matching the previous response shape; admin writes split internally into `AdminUsersService` (account) and `AdminUserProfilesService` (profile) while the route stays `PATCH /users/:id` with a single payload (`UpdateUserDto` composes `UpdateAccountDto` + `UpdateUserProfileDto`). Admin list/detail reads go through `AdminUsersReadService`, which joins both tables in one projected QueryBuilder query and never selects `passwordHash`.
- Routes (slice controllers under `src/identity/auth/<slice>/`, all under `/auth`): `POST register`, `GET verify-email?token=` (link target), `POST resend-verification` (`registration/`); `POST login` (single `identifier` = email or username), `POST refresh`, `POST logout` (all devices), `POST logout/current`, `POST logout/others`, `GET sessions`, `DELETE sessions/:id` (`session/`); `GET me`, `PATCH me` (profile), `PATCH password`, `POST delete-account`, `GET email` (pending change), `POST email`, `DELETE email`, `GET email/approve?token=` (non-mutating preview), `POST email/approve` with `{ token }` (applies the swap) (`account/`); `POST forgot-password`, `POST reset-password` (`recovery/`). Guarded routes use `JwtAuthGuard` + `@CurrentUser()`; `POST logout/current` uses `OptionalJwtAuthGuard` so it accepts an access token or the refresh cookie. The approve-email link is public because possession of the token authorizes the preview/swap.
- `JwtAuthGuard` loads the account on every request (a soft-deleted user is rejected: 401 `token_revoked` when deletion stamped the watermark, otherwise 401 `invalid_token`) and attaches `AuthenticatedUser = { id, isSuperuser, jti, accessExpiresAtMs }`, which the capability guards, session routes and targeted revocation rely on.
- Access tokens: JWTs signed with `JWT_SECRET`, 15 min TTL, claims `sub`, `jti`, `iat`, `iatMs`, `iss`/`aud` (`JWT_ISSUER` default `micurso`, `JWT_AUDIENCE` default `micurso-api`) and a `kid` header derived from the secret hash. `JWT_SECRET_PREVIOUS` is accepted for verification during rotation, so old tokens survive their short tail without honoring unverified/legacy claims. Revocation has two layers: per-token entries in the Redis ZSET `auth:denylist` (member = `jti`, score = expiry, idle TTL refreshed on every write; cap `AUTH_DENYLIST_MAX_SIZE`, default 100000 — expired entries are always pruned first, live entries are never evicted) and the `auth:revoked-before:<userId>` watermark for all-session revocation. The watermark compares the millisecond `iatMs` claim (not second-precision `iat`) so a token minted in the same second as a logout dies while a fresh re-login in that second survives.
- Refresh tokens: opaque 32-byte base64url strings; only their SHA-256 hash is stored (`refresh_tokens`), alongside an access-token journal (`accessJti`, `accessExpiresAt`) that lets targeted session revocation denylist the matching access token. 30-day rolling rotation; **reuse of a rotated token** is treated as theft and revokes every session of the user (atomic `UPDATE ... WHERE revokedAt IS NULL` claim). Presenting a token revoked by an explicit logout/revoke is merely invalid (401) and does not nuke the user's other devices.
- Sessions: `GET /auth/sessions` lists the caller's active refresh sessions with `current`, `createdAt`, `lastUsedAt` and `expiresAt`; login/rotation enforce `MAX_ACTIVE_SESSIONS` (default 10) by revoking the oldest session(s) and denylisting their access tokens. `DELETE /auth/sessions/:id` revokes one (404 `session_not_found`); `POST /auth/logout/current` revokes only the caller and accepts either an access token or the refresh cookie; `POST /auth/logout/others` keeps the caller and revokes the rest; `POST /auth/logout` logs out of **all** devices via the watermark. Targeted logouts never stamp the watermark, so the caller and the other devices stay alive; clearing the refresh cookie happens when the revoked session is the current one.
- Housekeeping: `TokenCleanupService` runs on a native `setInterval` (`AUTH_CLEANUP_INTERVAL_MS`, default 5 min; `unref()`ed, non-overlapping): prunes expired denylist entries, deletes `auth_tokens` 7 days past expiry, `refresh_tokens` 30 days past expiry, expired `email_change_requests`, and audit rows past `AUDIT_LOG_RETENTION_DAYS` (default 365).
- Browser storage: refresh token in an httpOnly + SameSite=Strict cookie scoped to path `/auth` (`Secure` only in production), so every `/auth/*` route can read it; writes also clear the legacy `/auth/refresh` cookie. Access token returned in the JSON body, meant for JS memory.
- Passwords: scrypt (N=32768, r=8, p=1, 64-byte key, raised `maxmem`), stored as `scrypt$N$r$p$salt$hash`; policy is ≥10 chars, upper+lower+digit, and no email local-part/username substring (substring checks only apply from 3 chars up). Change-password requires the current password and revokes all sessions (forced re-login); reset does the same. Unknown accounts still pay hashing cost (dummy hash) to keep login timing constant. Self-deletion (`POST /auth/delete-account` with the current password and `confirm: true`) soft-deletes the account, revokes every session and purges ephemeral rows.
- Rate limiting: the `RateLimiter` port (`src/rate-limit/rate-limiter.ts`) is bound in `RateLimitModule` to the cache-backed fixed-window adapter (`FixedWindowRateLimiter`); each flow owns its rules and builds `auth:rl:*`/`audit:rl:*` keys. Current limits: login 5/15 min per identifier + 20/15 min per IP; register 5/h/IP; forgot-password, resend-verification and email-change 3/h/identifier + 10/h/IP (email-change keys by account id); audit list 60/min per actor; a successful login clears its identifier counter.
- Verify/reset/approval tokens are single-use, stored SHA-256-hashed in `auth_tokens` (TTLs 24 h for verification, 1 h for reset and old-address email-change approval); anti-enumeration answers are generic. Emails/usernames are normalized (trim + lowercase) everywhere.
- Email change is sequential (`POST /auth/email` with the current password): a **verified** account stores a pending `email_change_requests` row and mails an approval link to its **current** address; `GET /auth/email` exposes the pending change, `GET /auth/email/approve?token=` only previews it, and `POST /auth/email/approve` with `{ token }` swaps the email unverified, revokes every session and mails the standard verification link to the new address. An **unverified** account changes immediately (still password-gated), also revoking sessions and starting verification. `DELETE /auth/email` cancels the pending request and kills its link. Applying an email change invalidates a pending password reset; a password change/reset cancels a pending email change. Admin email changes purge pending requests, clear verification, revoke sessions and invalidate reset tokens. Only actionable verification/approval/reset links are sent — there are no informational notifications.

## Authorization — attributes & groups
- Attributes are concrete `module:action` keys, never wildcards; each owning part exports its own manifest (`users/users.attributes.ts`, `groups/groups.attributes.ts`, `audit/audit.attributes.ts`) and definitions are merged by the tooling-only `attributes/attribute-registry.ts` (never imported at app runtime — no ABAC module). Current keys: `users:create|read|update|delete|assign_attributes`, `groups:create|read|update|delete|manage_members|manage_attributes` and `audit:read` (12 total).
- Tables: `attributes` (catalog incl. `deprecatedAt`), `user_attributes` (direct grants), `groups`, `group_attributes` (PK group+attribute → a group never repeats an attribute), `user_groups` (membership); all FKs cascade. Effective attributes = direct grants ∪ attributes of joined groups; superusers effectively hold the whole catalog.
- Seeder: `npm run db:migration:attributes -- src/database/migrations/Name` diffs the registry against the dev DB and writes a frozen migration (`import type` convention): inserts new keys, updates descriptions, marks removals deprecated — never deletes. The generator is idempotent; deprecate-never-delete keeps old grants resolvable.
- Enforcement is split by where the answer lives:
  - Access (request-only): `JwtAuthGuard` once per controller authenticates; each route declares its capability as a **named guard** — `@UseGuards(CanUpdateUsers)`, `CanManageGroupMembers`, ... Concrete guards subclass the abstract `AttributeGuard` (`identity/guards/attribute.guard.ts`) and encapsulate exactly one concrete key (`admin/users/users.guards.ts`, `admin/groups/groups.guards.ts`). The base enforces "authenticated AND (holds every key OR is superuser)" with 403 `insufficient_attributes`; the HTTP error carries the missing keys as `meta.required` — no metadata decorators. Concrete guards must declare an explicit constructor forwarding to `super(attributes)`: TypeScript only emits DI metadata for declared constructors.
  - Delegation (needs target context): the subset rule (`AttributesService.assertCanGrant`) lives in services: you may only grant/attach/add a member what you currently hold. Revoking, detaching and removing members are exempt — they never escalate.
  - State of other objects: policies are plain injectable classes **called in the flow**, never decorators — a guard cannot see loaded state. `SuperuserProtectionPolicy.assertCanModify(actor, target)` (403 `superuser_protected`) runs inside `AdminUsersService` after the target is loaded, for account/profile updates, deletion and grant/revoke. Superusers pass everywhere.
- Every `:id`/`:userId` route param uses `ParseUUIDPipe` (400 on malformed ids); no guard reads raw path params.
- Admin API (all in `src/admin/`): `GET/POST /users`, `GET/PATCH/DELETE /users/:id`, `POST /users/:id/restore`, `PUT/DELETE /users/:id/attributes/:key`; groups: `GET/POST /groups`, `GET/PATCH/DELETE /groups/:id`, `PUT/DELETE /groups/:id/attributes/:key`, `PUT/DELETE /groups/:id/members/:userId`; `GET /attributes` (catalog, any authenticated user); `GET /audit-logs` (`audit:read` or superuser, paged/filterable by action/actor/target/success/date). `GET /users` is offset-paged (`page` default 1, `limit` default 25, max 100), supports `status=active|deleted|all` (default active), `search` (case-insensitive partial match on email/username/first/last name, trigram-indexed), `emailVerified`, `isSuperuser` and whitelisted sorting (`sort` = `createdAt|email|username`, `order` = `asc|desc`; default `createdAt DESC`), always with the id tie-breaker; the composite `(createdAt, id)` index serves the default reverse scan. `GET /users/:id?withDeleted=true` reads a deleted row. User deletion is **soft**: the row survives (`users.deletedAt`), identifiers are released by partial unique indexes, and sessions/tokens/pending email changes are purged. `POST /users/:id/restore` accepts optional replacement `{ email, username }`; collisions answer 409 `restore_conflict` with `meta.conflicts`, replacing the email clears verification/sends the verification link, and restore always sets `passwordResetRequired`, sends a reset link and blocks login with 403 `password_reset_required` until reset (grants/memberships stay). Groups remain hard-deleted. There is **no self-service authorization surface** — regular users cannot read their effective attributes or groups. `isSuperuser` is never settable through the API (only `create-superuser` sets it); self-delete is blocked (400 `cannot_delete_self`) and user deletion cascades sessions.

## Architecture & style
- Keep each feature in its own NestJS module (controller → service → provider); apply SOLID without overengineering.
- Split by responsibility: `identity/` owns authentication, account/profile primitives and the authorization engine; `admin/` owns management use cases, capability guards, the catalog and audit read route; `audit/` owns the global trail and entity; `health/` owns probes/metrics. Admin sub-modules import `IdentityModule`; identity never imports admin.
- `src/common/` holds only genuinely cross-module utilities: `http/` (response envelope, pagination, exception filter, shared DTOs, validation flattening) and `swagger/` (document setup). Domain-specific types and services stay in their owning module.
- Document every function/module/class created: JSDoc/TSDoc for public APIs, inline comments for non-obvious logic.
- Keep naming, folder layout, and patterns deterministic so new code follows the established structure.
- Depend on abstractions: consumers inject interfaces/abstract classes; the concrete implementation is referenced only in its owning module's binding (`CacheModule`, `EmailModule`).

## Dependency decisions — user picks before install
- When implementing logic a package could handle, do not choose silently: first present the options in chat.
- Each option gets pros and cons, and the list must always include the native (no-dependency) approach.
- Wait for the user's choice before installing anything or writing the implementation.

## Security & configuration
- Never hardcode secrets, API keys, credentials, or URLs.
- `@nestjs/config` is wired globally (`ConfigModule.forRoot({ isGlobal: true })` in `AppModule`) and loads `.env` when `AppModule` is imported; `main.ts` keeps reading `process.env.PORT` directly, which is loaded before `listen` runs.
- Real credentials live only in the gitignored `.env`; `.env.example` is the committed template (`DATABASE_URL`, `DATABASE_URL_TEST`, `REDIS_URL`, `REDIS_URL_TEST`, `JWT_SECRET`, `APP_URL`, `PORT`, optional `JWT_SECRET_PREVIOUS`, `JWT_ISSUER`, `JWT_AUDIENCE`, `MAX_ACTIVE_SESSIONS`, `CORS_ORIGINS`, `EMAIL_OUTBOX_DIR`, `TRUST_PROXY`, `AUTH_DENYLIST_MAX_SIZE`, `AUTH_CLEANUP_INTERVAL_MS`, `AUDIT_LOG_RETENTION_DAYS`, `METRICS_TOKEN`). `configureApp` applies `TRUST_PROXY` to Express; leave it unset when directly exposed (trusting forwarding headers without a proxy lets clients spoof `request.ip`, which drives the rate limiter) and set the hop count or address list only behind a known proxy. `CORS_ORIGINS` is an explicit comma-separated allowlist with credentials; `*` is rejected at boot. `main.ts` enables Nest shutdown hooks so SIGTERM closes HTTP, Postgres and Redis. CLI scripts load `.env` explicitly via `node --env-file=.env`; test setup files use Node's native `process.loadEnvFile()`.
